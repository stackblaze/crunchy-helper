# pg-db-manager

Manage databases on a **Crunchy PGO (Postgres Operator)** cluster: list, create, delete, restore from pgBackRest, and manage users. Portable — run on any machine with cluster access.

## Prerequisites

- **Python 3.7+**
- **kubectl** in `PATH`, configured to talk to the Kubernetes cluster that runs PGO
- **Network access** to the cluster (kubeconfig or external API URL)

## Quick start (this machine)

```bash
cd pg-db-manager
pip install -r requirements.txt   # or: pip install PyYAML
./manager.py list                 # list databases (setup runs automatically if not configured)
./manager.py create               # create DB + user
./manager.py restore              # restore from backup
./manager.py users list           # list users
```
To run setup explicitly: `python -m pg_db_manager.setup`

## Portable use (another machine or cluster)

Use the same tool on a different host or against a different cluster by copying the project and (re)configuring it there.

1. **Copy the project** (no need to copy `pg-db-manager.env` — you will regenerate it):
   ```bash
   scp -r pg-db-manager user@other-host:
   # or: zip -r pg-db-manager.zip pg-db-manager -x "pg-db-manager/*.env" "pg-db-manager/__pycache__/*" "pg-db-manager/pg_db_manager/__pycache__/*"
   ```

2. **On the new machine**:
   ```bash
   unzip pg-db-manager-*.zip && cd pg-db-manager
   pip install -r requirements.txt
   ./manager.py   # setup runs automatically if not configured
   ```
   Point setup at the **kubeconfig** and **API server** for that cluster. It will create `pg-db-manager.env` for that environment.

3. **Run as usual**:
   ```bash
   ./manager.py list
   ./manager.py restore
   # etc.
   ```

**Using the same project for multiple clusters:** Either run from different copies of the folder (each with its own `pg-db-manager.env`), or use one copy and run `python -m pg_db_manager.setup` when you switch cluster (or set `PG_DB_MANAGER_ENV` to a different env file).

## Configuration

- **`pg-db-manager.env`** — Generated by setup (runs automatically or via `python -m pg_db_manager.setup`). Holds `KUBECONFIG`, `PG_HOST`, `NAMESPACE`, `CLUSTER`, etc. You can edit it by hand; use `${SCRIPT_DIR}` for paths under the project so the same file works when the folder is copied.
- **`PG_DB_MANAGER_ENV`** — Optional env var pointing to another env file (e.g. for a second cluster).

## Commands

| Command | Description |
|--------|-------------|
| `./manager.py list [--db NAME]` | List databases; optionally show connection info for one |
| `./manager.py create [--db NAME] [--user USER] [--password PASS]` | Create database and user |
| `./manager.py delete [--db NAME] [--yes]` | Delete a database |
| `./manager.py restore [--backup LABEL] [--source-db NAME] [--as NAME] [--yes]` | Restore a DB from pgBackRest (PVC + restore/extract pods, same flow as restore-db.sh) |
| `./manager.py users list` | List PostgreSQL users |
| `./manager.py users create/delete/reset-password` | Manage users |

## Restore flow

Restore follows the same process as the production `restore-db.sh` script:

1. PVC per (database, backup date); reuse if data already restored.
2. Restore pod: pgbackrest restore from S3 to PVC (if needed).
3. Extract pod: temp Postgres on PVC → pg_dump → dump on PVC.
4. Copy dump to primary; CREATE DATABASE + pg_restore on primary.

The `pgbouncer` schema is excluded from restore so it doesn’t conflict with PGO-created objects.
